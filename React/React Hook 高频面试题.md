##### 1. 什么是 Hook？为什么 React 要引入 Hook？

> Hook 是 “把可复用的状态逻辑接入函数组件” 的机制。它让函数组件拥有状态、上下文、ref、effect 等能力，避免很多类组件里 `this`、生命周期拆散逻辑、HOC/render props 嵌套过深的问题。本质上，Hook 不是语法糖，而是 React 在函数组件渲染过程中管理状态和副作用的一套协议。

##### 2. 为什么 Hook 只能在组件顶层调用，不能写在 if、for、回调里？

> React 依赖 Hook 的“调用顺序” 来把每一次 Hook 调用和对应的状态槽位匹配起来。官方规则明确说，每次渲染时 Hook 必须按完全相同的顺序调用；一旦条件分支导致顺序变化，React 就会把后续 Hook 对错状态，出现 “Rendered fewer / more  hooks than expected” 之类错误。

##### 3. React 是怎么记住多个 useState / useEffect 的？

> React 官方源码 `ReactFiberHooks.js` 可以看到，Hooks 会挂到当前组件对应的 Fiber 的 `memoizedState` 上，并串成链表。渲染时 React 按调用顺序向后遍历，所以第一个 `useState` 永远匹配第一个槽位，第二个匹配第二个槽位。**Hooks 靠调用顺序定位，靠 Fiber 保存状态**

##### 4. useState 的本质是什么？调用 setState 后发生了什么？

> `useState` 返回“当前状态快照 + 更新函数”。调用 `setX` 不会立刻修改当前这次执行中的变量，而是把更新加入队列，随后触发下一次渲染；下一次渲染时 React 取出队列并计算新状态，再更新 UI。所以在同一个事件回调里 `console.log(state)`，看到的通常还是旧值。

**5. 为什么连续执行三次 setCount(count + 1)，结果不一定是加 3？**

> 因为当前事件回调里拿到的 count 是这次渲染的快照，同一次回调里的三个 `count + 1` 可能都是基于同一个旧值计算出来的。正确写法是 `setCount(c => c + 1)`，让 React 在更新队列里按顺序把前一个结果传给后一个 `updater`。

**6. 为什么 useState 支持传函数？useState(() => expensiveInit()) 有什么意义？**

> 这是惰性初始化。初始化函数只在首次渲染时用于计算初始值，后续渲染会忽略这个初始参数。适合把昂贵初始化延后到真正挂载时做，而不是每次 render 都重新算。

**7. useState 和 useRef 的本质区别是什么？**

> `useState` 保存的是 “影响视图的数据”，更新后会触发重渲染； `useRef` 保存的是 “不参与渲染的数据引用”，`ref.current` 改变不会触发重渲染。`useRef` 在后续渲染中会返回同一个对象，所以它很适合存 DOM、定时器 ID、上一次值等。

**8. 为什么改 ref.current 不会触发重新渲染？**

> 因为 React 不把 `ref.current` 当成响应式数据源。ref 更像一个稳定的可变盒子，React 只保证这个盒子对象本身稳定，不会监听里面字段的变化。换句话说，`ref` 是 `escape hatch`，不是响应式状态。

**9. useEffect 的本质到底是什么？是不是“组件挂载后执行”？**

> `useEffect` 本质是 **让组件与外部系统同步**，不是单纯替代生命周期。它发生在 commit 之后，适合处理订阅、DOM API、网络连接、定时器、第三方库等 “React 之外” 的系统。官方还特别强调：如果你不是在同步外部系统，很多时候你根本不需要 Effect。

**10. useEffect 的执行时机和清理时机是什么？**

> 组件 commit 后执行 setup；依赖变化后，先执行上一次 cleanup，再执行新的 setup；组件卸载时，再执行一次最终 cleanup。
> **mount 执行 setup，update 先 cleanup 再 setup，unmount 执行 cleanup。**

**11. 为什么 useEffect 在开发环境里会执行两次？这是 bug 吗？**

> 不是。React 在 Strict Mode 下会额外执行一次 "setup->cleanup->setup"，这是开发期压力测试，用来检查你的副作用是否可正确清理。它不影响生产环境，如果这个行为导致问题，往往说明 cleanup 没写对。

**12. useEffect 为什么会死循环？**

> 官方给出的判断很直接：必须同时满足两件事，才会无限循环。第一，Effect 里更新了某个 state；第二，这个 state 的变化又让 Effect 的依赖发生变化，于是再次执行。最常见的诱因是依赖了每次 render 都新建的对象或函数。

**13. 依赖数组是怎么比较的？为什么对象/函数经常导致重复执行？**

> React 对依赖项使用 `Object.is` 比较。基本类型通常按值稳定，对象和函数如果在 render 里重新创建，每次引用都不同，因此依赖会被判定为“变了”。这也是为什么很多 Effect 会被临时对象、内联函数反复触发。

**14. 什么是闭包陷阱（stale closure）？为什么 Hook 里特别容易问这个？**

> 函数组件每次渲染都会生成一套新的作用域；事件处理函数、定时器回调、Effect 回调捕获的是 “创建它那次渲染” 的变量快照。如果你没把依赖写全，或者异步回调运行得更晚，就可能读到旧状态。
> 
> 解决思路通常有 4 种：补全依赖、用 `updater function`、用 `useRef` 保存最新值、或者在合适场景下用 `useEffectEvent`。

**15. useLayoutEffect 和 useEffect 的差别是什么？**

> `useLayoutEffect` 会在浏览器重绘前执行，适合做布局测量、同步读写 DOM；`useEffect` 在绘制之后执行，更适合大多数副作用。前者会阻塞浏览器绘制，性能成本更高，所以官方明确建议“能用 useEffect 就优先用 useEffect”。

**16. useMemo 的本质是什么？能不能把它当成“语义保证”？**

> `useMemo` 是 **缓存计算结果的性能优化**，不是语义保证。依赖不变时，React 复用上次结果；依赖变了才重新计算。但官方也说明，React 在某些场景下会丢弃缓存，所以不能把 `useMemo` 当作 “功能正确性必须依赖的存储机制”。没有它就错，说明设计本身有问题。

**17. useCallback 的本质是什么？为什么很多时候“滥用”它？**

> `useCallback(fn, deps)` 本质上是在缓存函数引用，常见用途是配合 `memo` 避免子组件无意义重渲染，或避免把新函数引用塞进 `Effect` 依赖项里。它也是性能优化手段，不是默认必需品。React 官方现在还特别强调：React Compiler 会自动做一部分 memoization，手写 useCallback 的必要性比过去更低。

**18. useReducer 和 useState 的底层思路有什么不同？**

> 两者都是状态 Hook，但 `useReducer` 把 “状态如何变化” 收敛到 reducer 里，适合复杂状态迁移、多个子值联动、可预测事件流。它返回 `[state, dispatch]`，其中 dispatch 身份稳定。
> 
> 面试常见回答：**useState 更像直接赋值，useReducer 更像事件驱动的状态机。**

**19. useContext 为什么会让消费组件重新渲染？memo 能挡住吗？**

> `useContext` 不只是“读取”，它还会订阅 context。Provider 的 `value` 变化后，React 会让使用这个 context 的后代重新渲染，比较方式同样是 `Object.is` 。官方明确说明：即使子组件用了 `memo`，也不能阻止它收到新的 context 值。
> 所以 context 性能优化重点通常在于稳定 `value` 引用和拆分 context。

**20. 自定义 Hook 的原理是什么？为什么它本身也必须遵守 Hook 规则？**

> 自定义 Hook 本质不是 React 特殊语法，只是“封装了一组 Hook 调用的函数”。它之所以也必须在顶层调用，是因为它内部仍然会触发原生 Hook 的顺序匹配机制。也就是说，自定义 Hook 复用的是“状态逻辑”，不是“状态实例”；每个调用它的组件仍然拥有自己的独立状态。

**21. useImperativeHandle 是做什么的？它为什么不符合 React 声明式思想？**

> 它允许子组件自定义通过 ref 暴露给父组件的句柄，比如只暴露 focus()、scrollIntoView()，而不是整个 DOM。它属于命令式 escape hatch。
> 官方建议很明确：**如果能用 prop 表达，就不要用 ref。** 所以它常被问作“你是否理解声明式和命令式边界”。

**22. React 19 里的 useEffectEvent 解决了什么问题？**

> 它用于把 “Effect 中的事件逻辑” 和 “Effect 的响应式同步逻辑”拆开。它读取的始终是最新的 render 的值，但不会因此让外层 Effect 重跑。适合处理定时器、订阅回调、监听器里 “想读最新值，但不想重新订阅”的场景。注意它不是拿来逃避依赖数组的，官方明确反对这么用。

**23. useTransition 的原理是什么？它和普通更新有什么区别？**

> 它把一部分更新标记为非阻塞更新，让更紧急的交互先响应，过渡中的 UI 在后台渲染。可以理解为 “给更新分优先级”。所以输入框这类强交互状态通常不能直接放进 tansition，否则会感觉卡顿或延迟。

**24. useSyncExternalStore**

> 因为它代表了 React 与“外部状态源”正确对接的标准方式。它要求你提供 subscribe 和 getSnapshot，React 负责在 store 变化时重新读取快照并判断是否更新。

**25. 为什么 use 和普通 Hook 不完全一样？**

> 官方现在把 use(resource) 单独列出来，它可以读取 Promise 或 context，而且与普通 Hook 不同，它可以出现在条件和循环里。
> 
> 面试里如果被问到这一点，说明对方想确认你知道：**“Rules of Hooks” 有一个特殊例外，就是 use。**

**26.  为什么说 state 是“快照（snapshot）”？**

>  React 官方把 `state` 描述成 “某次渲染时的快照”。函数组件执行时，拿到的事这一次 render 对应的 state 值；即使在事件里调用了 `setState`，当前这次函数作用域里的变量也不会变，新的 state 只会出现在下一次渲染里。

**27. setState 为什么有时看起来是“异步”的？**

> 更准确地说，它不是传统意义上的 Promise 异步，而是 “不会同步改当前渲染快照”。React 会把更新排队，再在合适时机触发下一轮渲染，所以开发者体感上像 “异步”。
> 
> 避免直接回答 “setState 就是异步”，而是说 “它是调度更新，不是立刻改变量”。

**28. React 为什么要批量更新（batching）？**

> 批量更新可以把同一轮交互中的多个状态变更合并，减少不必要的重复渲染，提高性能并保持 UI 一致性。React 18 以后自动批量更新范围更广，很多异步场景也会合并。

**29. 如果 setState 传入的新值和旧值一样，会不会重新渲染？**

> React 会用 `Object.is` 比较新旧 state。如果结果相同，通常会跳过这次无意义更新。
> 这不是完全什么都不做，而是 React 会尽量跳过不必要的重新渲染和提交。

**30. useReducer 的 dispatch 为什么通常不用写进依赖数组？**

> 因为 dispatch 的引用是稳定的，React 不会在每次 render 都给你一个新的 dispatch。这和很多普通内联函数不一样，所以它一般不是依赖变化源。

**31. useEffect 里不写依赖数组、写空数组、写具体依赖，区别是什么？**

> 不写依赖数组，每次 commit 后执行；
> 写 `[]`：只在首次挂载后执行一次，卸载时清理；
> 写 `[a,b]`：首次执行，之后只有 a 或 b 变化时才重新执行。
> 
> 注意：`[]` 不是 “组件生命周期替代品”，而是 “这个 effect 不依赖响应式值”。

**32. 为什么官方强调“依赖项不能随便少写”？**

> 因为 Effect 应该准确描述它依赖了哪些响应式值。少些依赖，本质是在骗 React：“这些值变化了也不需要重新同步”。这样非常容易出现 state closure、订阅对象不更新、请求参数还是旧值等隐蔽 bug，所以才有 `exhaustive-deps` 规则。

**33. 那为什么有时又要“移除不必要的依赖”？**

> 不是靠“少些”依赖，而是靠 “重构代码” 让依赖本来就不需要存在。比如把对象创建移到 Effect 内、把状态更新改为 updater function、把非响应式逻辑提取出去。重点是 “让依赖真实变少”，而不是 “手工删依赖”。

**34. 为什么在 render 阶段不能做副作用？**

> 因为 React 要求组件和 Hook 保持纯净。render 可能被重复执行、打断、丢弃；如果你在 render 阶段发请求、改 DOM、订阅事件，就会造成重复执行或脏状态。副作用必须放到 Effect 节点，因为那是 commit 后真正“落地”的阶段。

**35. useMemo 为什么不能拿来替代 useEffect？**

> `useMemo` 只负责缓存 “纯计算结果”，不应该产生副作用；它运行在 render 期间，而 render 必须纯净。像请求、订阅、操作 DOM 这种都必须放在 Effect，而不是 `useMemo` 里做。

**36. useCallback(fn, deps) 和 useMemo(() => fn, deps) 有什么关系？**

> 本质上 `useCallback` 可以理解为 `useMemo` 缓存函数引用的语法化封装。前者语义更清晰，表示 “我要缓存这个函数本身”；后者更泛化，表示 “我要缓存这个计算结果”。

**37. 自定义 Hook 会不会共享内部 state？**

> 不会。自定义 Hook 共享的是逻辑，不共享实例状态。每个组件调用一次自定义 Hook，React 都会在该组件自己的 fiber 上建立一套独立 Hook 状态链。

**38. 为什么说 Hook 让“逻辑复用”比 HOC/render props 更自然？**

> 因为 Hook 复用的是行为和状态组织方式，而不是额外的组件层级或 props 嵌套。它把“订阅逻辑” ”请求逻辑“ “表单逻辑” 封装成函数，直接结合在组件内部，横向复用更自然，树结构也更干净。

**39. useContext 为什么容易引发性能问题？**

> 因为只要 Provider 的 `value` 引用变了，所有消费该 `context` 的组件都可能重新渲染。最常见问题是每次 render 都传一个新对象： `value={{ a, b }}。` 这会导致消费者频繁更新，所以常见优化是拆分 `context`、稳定 `value` 引用、缩小订阅范围。

**40. useRef 和闭包都能“记住值”，它们区别是什么？**

> 闭包记住的是某次创建函数时的变量快照；`useRef` 记住的是跨 render 持久存在的同一个对象。闭包容易“旧”，`ref.current` 则可以被手动更新为“最新”。所以处理异步回调里的最新值时，`ref` 常是重要手段。

**41. 为什么 useEffect 获取到的有时是旧值，而事件处理函数常常是新值？**

> 两者都基于闭包，但创建时机不同。事件处理函数通常跟随最新 render 重新创建并绑定，所以用户下一次点击时，往往会执行较新的闭包；而某些定时器、订阅回调如果是在旧 effect 里注册的，就会一直持有旧闭包，直到 effect 重新执行并重新注册。

**42. useId 的原理和用途是什么？为什么 SSR 场景常被问？**

> `useId` 用于生成在客户端和服务端都稳定一致的 ID，避免 hydration 时 ID不匹配。它主要服务于可访问性关联，比如 `label` 和 `input` 的 `id/htmlFor` 绑定，不适合拿来当列表key。

**43. 为什么 key 和 Hook 状态有关？**

> Hook 状态是挂在组件实例对应 fiber 上的，而 `key` 决定 React 如何识别 “是不是同一个组件实例”。如果 `key` 变了React 往往会把它视为新实例，原来的 Hook 状态会被销毁并重新初始化。

**44. 为什么切换条件渲染时，组件 state 有时会保留，有时会重置？**

> 核心看 React 是否认为它们是 “同一个位置上的同一个组件”。如果组件类型、层级位置、key 都保持一致， state 通常会保留；如果位置变化或 key 变化，React 会重建实例，Hook 状态随之重置。

**45. useDeferredValue 和 useMemo 的区别是什么？**

> `useMemo` 是缓存计算结果；`useDeferredValue` 是延迟一个值的更新优先级。前者解决“重复计算”，后者解决“高优先级交互不要被低优先级内容拖慢”。
> 
> 重点回答“一个是缓存，一个是调度”。

**46. useInsertionEffect 是做什么的？为什么普通业务几乎不用？**

> 它主要给 CSS-in-JS 库用，用来在布局 effect 读取样式前把样式插入 DOM。它执行得非常早，属于更底层的时机控制。普通业务组件一般不需要，面试问到通常是想区分你是否知道它的定位非常特殊。

**47. 为什么会出现 “Invalid hook call” 错误？**

> 常见原因有三个。第一，违反 Hooks 调用规则；第二，React 和渲染器版本不匹配；第三，项目里出现了多个 React 副本。面试里这是个很经典的排障题


 **48. 能不能在普通工具函数里调用 Hook？**

> 不能，除非它本事是 React 组件或自定义 Hook。因为 Hook 依赖 React 当前渲染上下文，普通函数没有对应 fiber 和渲染流程，React 无法为它分配和追踪 Hook 状态。

**49. 为什么说“不是所有逻辑都应该抽成 Hook”？**

> 因为 Hook 的价值在于封装 “与 React 生命周期/状态系统绑定的逻辑”。如果只是纯函数计算、字符串处理、对象转换，抽成普通工具函数更合适。

**50. 一句话总结 Hook 原理，怎么说？**

> React 在函数组件渲染时，按固定调用顺序把每个 Hook 映射到 fiber 上保存的状态槽位；状态更新会触发新一轮渲染，Effect 在 commit 后负责把组件与外部系统同步。

 **51. 为什么不要把“派生状态”再存一份到 useState？**

> 如果一个值可以由 props 或其他 state 直接计算出来，就不应该单独再存一份，否则容易出现双写不一致。
> **能算出来的值优先在 render 中计算，除非计算特别贵再考虑 useMemo.**

**52. 为什么有些 Effect 应该拆成两个，而不是写成一个大 Effect？**

> 因为一个 Effect 只应负责一类同步逻辑。把 “订阅Websocket” 和“同步 document.title" 写在一起，会让依赖纠缠、清理逻辑混乱。拆分后，每个 Effect 的依赖和生命周期都更清晰。

**53. 为什么请求数据时容易写出有 bug 的 useEffect？**

> 因为请求有竞态问题。比如旧请求比新请求更晚返回，就可能把新结果覆盖掉。
> 如何处理？常见答案包括 cleanup 里忽略旧请求、AbortController、或上层数据框架接管请求缓存与竞态。
> 
> 实际中用 `useOnceSWR` 

**54. 为什么 useEffect 里要返回 cleanup，而不是在别处手动卸载？**

> 因为 React 的副作用模型是“建立什么，就在对应 cleanup 中撤销什么”。这样当依赖变化或组件卸载时，React 才能正确回收上一次副作用，避免内存泄漏和重复订阅。

**55. 为什么 memo + useCallback 不一定能优化性能？**

> 它们本身也有比较和缓存成本。如果子组件很轻、父组件渲染不频繁，强行 memo 可能收益很低。**先看重渲染成本和传参稳定性，再决定是否需要记忆化。**

**56. 为什么列表项里的组件切换顺序会影响 Hook 状态？**

> 本质上还是实例身份问题。React 根据位置和 key 判断哪个 fiber 对应哪个组件实例；实例一旦错位，原本挂在 fiber 上的 Hook 状态也会 “跟着实例识别逻辑走”，这就是列表错 key 时状态串位的根源。

React 18/19 常见新知识点：

**57. startTransition 和 useTransition 的区别是什么？**

> `startTransition` 是 API，用来把某次更新标记为低优先级；`useTransition` 是 Hook，除了提供 `startTransition`，还额外提供 `isPending` 用于展示过渡状态。一个偏能力，一个偏组件内状态感知。

**58. 为什么 transition 不能直接控制文本输入值？**

> 输入框值属于高优先级、强交互更新，必须立刻响应。Transition 适合列表筛选结果、详情区切换、耗时内容刷新这类 “可以稍后完成” 的更新；如果把输入值本身放进去，会造成输入延迟。

**59. useDeferredValue 的本质为什么不是“防抖”？**

> 防抖是基于时间延迟，`useDeferredValue` 是基于更新优先级延后显示。它不会承诺等多久，只会让高优先级更新先走。所以它更像 “渲染调度工具”，不是传统节流/防抖工具。

**60. useFormStatus 为什么必须在 form 内部子组件里用才有效？**

> 因为它读取的是最近一次表单提交上下文。官方文档明确指出，它不是读取“当前组件自己声明的 form”，而是读取它所在表单上下文中的提交状态，所以位置不对就拿不到正确 pending。

**61. 为什么 useSyncExternalStore 比“自己在 Effect 里订阅 store”更标准？**

> 因为它把订阅和快照读取协议正式化了，能更好地适配并发渲染和一致性要求。手写 `useEffect + subscribe` 容易出现快照不一致、更新时机不稳的问题，而 `useSyncExternalStore` 是 React 官方给外部 store  接入的标准解法。
