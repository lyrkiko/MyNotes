Agent 的输出不只是“最终回答”。真实项目里，它通常会输出 **文本、事件、工具调用、结构化数据、文件、状态变更、人工确认请求** 等多种东西。

  
可以先把 Agent 输出理解成四层：

```text

LLM token 输出

-> Agent 运行事件

-> 工具调用与工具结果

-> 最终结果 / 文件 / 状态变更

```

  
**1. 普通同步输出**

最简单的形式：
  
```http

POST /agent/run

-> 等待

-> 返回完整结果

```


例如：
```json

{

"answer": "这个 PR 主要修改了登录逻辑...",

"status": "completed"

}

```

原理是后端等待 Agent 完整执行结束，再一次性返回结果。

适合：
- 任务很短
- 不需要展示中间过程
- 结果必须完整校验后才能返回
- 后端 API 调用，而不是聊天体验

缺点是用户要一直等，看不到 Agent 是否卡住。

  

**2. 流式文本输出**

“流式输出”，常见于聊天界面。

形式类似：

```text

我正在分析...

这个 PR 的主要变化是...

1. 修改了登录接口...

2. 增加了 token 校验...

```

原理是模型生成文本时，本来就是一个 token 一个 token 生成的。服务端不等全部生成完，而是把增量内容实时推给前端。

常见技术：
- SSE：`text/event-stream`
- WebSocket
- Fetch ReadableStream

前端收到一小段就渲染一小段。

适合：
- Chat UI
- 长文本生成
- 总结、解释、代码生成
- 用户需要感知“正在进行中”

采纳原因：
- 体感速度更快
- 用户等待焦虑更低
- 可以支持中途取消
- 更接近真实对话体验

但要注意：流式文本不适合直接当可靠数据源，因为中间内容可能还没完成，不能边流边当最终 JSON 使用。

  
**3. Agent 事件流输出**

比“流式文本”更工程化。

不是只输出文字，而是输出一系列事件：

```json

{ "type": "run_started" }

{ "type": "message_delta", "text": "我先查询相关 issue..." }

{ "type": "tool_call", "tool": "searchIssues", "args": { "keyword": "login" } }

{ "type": "tool_result", "tool": "searchIssues", "count": 8 }

{ "type": "message_delta", "text": "我找到了 8 个相关 issue..." }

{ "type": "run_completed" }

```

原理是 Agent Runtime 在每个关键节点发事件：开始、模型输出、工具调用、工具返回、状态切换、等待人工确认、完成、失败。

适合：
- 可视化 Agent 执行过程
- 展示工具调用
- 做 trace / debug
- 长任务
- 工作流 Agent
- 前端需要知道“Agent 正在做什么”

采纳原因：
- 可观测性强
- 前端体验更清楚
- 方便排查问题
- 方便做人工介入
- 比纯文本流更适合真实产品

在 NestJS 里，事件流通常用 SSE 或 WebSocket 实现。

**4. 结构化输出**

Agent 不返回自然语言，而返回符合 schema 的数据。

例如：
```json
{
"summary": "本次 PR 修改了登录鉴权逻辑",
"riskLevel": "medium",
"tasks": 
	[
		{
	
			"title": "补充 token 过期测试",
			"priority": "high"
		}
	]
}
```

原理是给模型明确 JSON Schema / Zod Schema，让模型按结构输出。有些模型或框架支持严格结构化输出；不支持时通常要做解析、校验、失败重试。

适合：
- 前端表单填充
- 任务拆解
- 分类判断
- 风险评级
- 自动化流程的下一步输入

采纳原因：
- 程序可消费
- 可校验
- 方便落库
- 方便驱动 UI
- 比自然语言更稳定

注意：结构化输出通常应该等最终完成后再返回，不建议把未完成 JSON 直接流给前端。

  
**5. 工具调用输出**

Agent 有时不会直接回答，而是输出“我要调用某个工具”。
例如模型先输出：
```json

{

"tool": "getPullRequest",

"arguments": {

"repo": "demo",

"prNumber": 12

}

}

```

然后 Agent Runtime 执行真实函数：

```ts

getPullRequest({ repo: 'demo', prNumber: 12 })

```

工具返回结果后，再交给模型继续推理。

原理是 LLM 负责“判断该调用什么工具以及参数是什么”，后端负责“真正执行工具并把结果回填给模型”。

适合：
- 查数据库
- 调 GitHub API
- 读文件
- 搜索知识库
- 创建任务
- 发消息、下单、审批等操作


采纳原因：
- 让 Agent 连接真实系统
- 避免模型凭空编造
- 让业务逻辑仍由代码控制
- 权限、审计、风控可以放在工具层

重要原则：高风险工具调用不要自动执行，应该输出“操作提案”，等待用户确认。

  

**6. 人工确认输出**

Agent 输出的不是答案，而是一个等待用户决策的状态。
例如：
```json

{

"type": "approval_required",

"action": "createIssue",

"preview": {

"title": "补充登录失败测试",

"body": "建议增加 token 过期和密码错误场景"

}

}

```

原理是 Agent 运行到高风险节点后暂停，把待执行动作发给前端。用户批准、修改或拒绝后，Agent 再继续。

适合：
- 创建 issue
- 发送邮件
- 修改代码
- 删除数据
- 提交订单
- 调用外部系统写操作 

采纳原因：
- 降低误操作风险
- 符合真实业务流程
- 保留用户控制权
- 方便审计责任

这类模式在工作流 Agent 中非常重要。

  
**7. 异步任务输出**

有些 Agent 任务太长，不能靠一个 HTTP 请求等完。
形式通常是：

```json

{

"jobId": "agent_run_123",

"status": "running"

}

```

然后前端通过轮询、SSE 或 WebSocket 获取进度。
原理是请求进来后，后端把任务放入队列，比如 BullMQ / Redis。Agent 后台执行，状态持久化到数据库。

适合：
- 大文档分析
- 批量代码审查
- 长时间 RAG 构建
- 多步骤工作流
- 需要失败重试的任务


采纳原因：
- 避免 HTTP 超时
- 支持暂停、恢复、重试
- 后端更稳定
- 可以做任务队列和并发控制

  

**8. 文件或 Artifact 输出**

Agent 最终生成一个文件、报告或资源，而不是只返回文本。
例如：

```json

{

"type": "artifact",

"fileName": "pr-review-report.md",

"mimeType": "text/markdown",

"url": "/files/pr-review-report.md"

}

```

  

适合：
- Markdown 报告
- Excel
- PPT
- 代码补丁
- 测试报告
- 架构图

  

采纳原因：
- 结果可沉淀
- 适合复杂内容
- 方便下载、预览、版本管理
- 比聊天记录更适合交付

  

**9. UI 状态输出**

Agent 可以直接输出前端状态，而不是文本。
例如：
```json

{

"view": "task_list",

"items": [

{ "title": "补充登录测试", "done": false },

{ "title": "检查鉴权中间件", "done": false }

]

}

```

原理是 Agent 生成结构化 UI state，前端根据状态渲染组件。

适合：
- 看板
- 表单
- 审批流
- 搜索结果页
- 多步骤任务界面

采纳原因：
- 比纯聊天更产品化
- 用户可以直接操作结果
- 适合前端工程师发挥优势
- 方便把 Agent 嵌入现有业务系统


**如何选择输出模式**

可以按这个原则选：
| 需求 | 推荐输出模式 |

| --- | --- |

| 简单问答 | 同步输出 |

| 聊天体验 | 流式文本 |

| 展示执行过程 | Agent 事件流 |

| 前端要消费数据 | 结构化输出 |

| 要连接系统能力 | 工具调用输出 |

| 有高风险写操作 | 人工确认输出 |

| 长任务 | 异步任务输出 |

| 生成交付物 | 文件 / Artifact 输出 |

| 嵌入业务系统 | UI 状态输出 |

  

对你学习 NestJS + Agent 来说，建议按这个顺序实现：
1. 先做同步输出。
2. 再做 SSE 流式文本。
3. 然后升级成 Agent 事件流。
4. 再加结构化输出和工具调用。
5. 最后做异步任务、人工确认和 Artifact。

  

真实 Agent 产品里，最常用的组合其实是：

```text

SSE 事件流

+ message_delta 文本增量

+ tool_call / tool_result 事件

+ approval_required 人工确认

+ final_result 结构化结果

```

  
也就是说，流式输出只是 Agent 输出体系中的一部分。更完整的 Agent 应用，核心是“把执行过程事件化，把最终结果结构化，把高风险动作确认化”。
