HTTP 轮询（Polling）是一种用于解决“客户端如何实时获取服务器最新数据”的早期技术方案。它的核心思想是**“客户端主动拉取”**，而非“服务器主动推送”。

根据实现方式的不同，HTTP 轮询主要分为两种模式：**短轮询（Short Polling）**和**长轮询（Long Polling）**。两者的工作机制和性能开销天差地别。

#### 1. 短轮询（Ajax 轮询）

这是最传统、最朴素的方式，类似于“闹钟式”的询问。

- **工作流程**：客户端（浏览器）每隔固定的时间（如 3 秒）向服务器发起一次 HTTP 请求，询问“有新数据吗？”服务器收到请求后，无论有没有新数据，都立即返回响应（有数据就带数据，没数据就返回空）。
    
- **特点**：实现极其简单，只需在前端用 `setInterval` 或 `setTimeout` 循环调用接口即可。
    
- **致命缺陷**：
    
    - **资源浪费**：绝大多数请求都是无效的（空响应），浪费了客户端的带宽和 CPU，也加重了服务器的 QPS（每秒查询率）压力。
        
    - **实时性差**：如果数据在刚请求完后的 0.1 秒产生，客户端必须等待下一个 3 秒周期才能获取到，存在延迟（延迟时间 = 轮询间隔）。
        
    - **TCP 握手开销**：每次请求都要经历 TCP 三次握手和四次挥手（HTTP/1.1 下 Keep-Alive 虽可复用连接，但空转依然有开销）。

#### 2. 长轮询（Long Polling / Comet）

这是对短轮询的改进，属于“半推半拉”模式，也是 WebSocket 普及前最主流的实时方案。

- **工作流程**：客户端发起一个 HTTP 请求到服务器，服务器**不立即返回**，而是“挂起”这个连接（Hold住）。服务器会等待数据变化或超时。
    
    - **如果有新数据**：服务器立即利用这个挂起的连接返回响应，客户端收到数据后，**立刻**再发起一个新的长轮询请求，形成“请求-等待-响应-立即再请求”的循环。
        
    - **如果无数据且超时**（如设定了 30 秒）：服务器返回一个空响应或超时信号，客户端收到后，**立刻**重新发起一个新的长轮询请求。
        
- **特点**：实现了“类推送”效果，数据几乎能实时到达客户端。

| 维度        | 短轮询           | 长轮询                          |
| --------- | ------------- | ---------------------------- |
| **实时性**   | 低，取决于间隔时间     | 高，有数据立即返回                    |
| **服务器压力** | 极高（高频无意义的空请求） | 中等（请求次数少，但占用连接数）             |
| **连接状态**  | 短连接，请求结束即断开   | 连接会保持较长时间（半长连接）              |
| **服务器资源** | 消耗 CPU 处理请求   | **消耗内存和端口**（挂起的连接会占用系统文件描述符） |
| **实现难度**  | 极简            | 需处理超时、重连、并发连接数限制             |
|           |               |                              |

#### 为什么长轮询仍然不够完美？（痛点）

虽然长轮询比短轮询优秀，但在高并发场景下存在明显的 **连接数黑洞** 问题。因为每个客户端都要长期占用一个 HTTP 连接，而浏览器对同一域名下的并发连接数有限制（HTTP/1.1 通常为 6 个），如果用户打开多个标签页，长轮询会迅速占满连接池，导致其他正常请求（如加载图片、CSS）被阻塞。

此外，长轮询需要服务端代码专门维护挂起的请求列表（如使用 `DeferredResult`（Spring）或 `AsyncContext`（Servlet）），增加了后端逻辑的复杂度。


#### 现代替代方案（补充）

如今，轮询模式已逐渐被更高效的技术取代：

1. **Server-Sent Events (SSE)**：基于 HTTP 的长连接，服务端可以单向持续推送数据给客户端（适合新闻推送、股票行情），比长轮询更轻量，且自动支持断线重连。
    
2. **WebSocket**：真正的全双工通信，建立连接后客户端和服务端可以随时互相发送数据，没有 HTTP 头部开销，性能最佳（适合聊天、游戏）。

#### SSE TCP+TLS 握手

SSE（Server-Sent Events）的握手过程与发起一个普通的HTTPS请求**完全一致**。它不像WebSocket那样需要协议升级[](https://developer.aliyun.com/article/1617441)，就是一次标准的、建立在`TCP + TLS`之上的HTTP请求。

具体的握手流程可以拆解为以下三个阶段：

##### 阶段一：TCP三次握手（建立连接）

这是所有HTTP通信的基础，目的是在客户端和服务器之间建立一个可靠的传输通道。过程如下：

1. **第一次握手（SYN）**：客户端向服务器发送一个SYN（同步序列编号）包，询问服务器是否准备好建立连接。
    
2. **第二次握手（SYN-ACK）**：服务器收到后，回复一个SYN-ACK包，表示“我准备好了”。
    
3. **第三次握手（ACK）**：客户端收到服务器的确认后，再发送一个ACK（确认）包。至此，TCP连接建立成功。
    

这个连接建立后，会通过HTTP的`Keep-Alive`机制维持住，不会因为一次请求就关闭，而是为后续的持续数据传输服务[](https://developer.baidu.com/article/detail.html?id=6226296)。


#### 阶段二：TLS四次握手（建立安全通道）

如果你的SSE服务使用`https://`协议（这是生产环境的标配），那么TCP连接建立后，会立刻进行TLS（传输层安全协议）握手，来协商如何加密通信。这个过程通常包括：

1. **客户端发起“Client Hello”**：客户端发送它支持的TLS版本和加密算法列表。
    
2. **服务器回应“Server Hello”**：服务器从中选择一套算法，并发送自己的证书（包含公钥）给客户端[](https://datasea.cn/go0212483374.html)。
    
3. **密钥交换与验证**：客户端验证服务器证书的合法性[](https://datasea.cn/go0212483374.html)，双方通过协商的算法生成用于本次会话的对称加密密钥。
    
4. **“Finished”消息**：双方发送加密的“Finished”消息，确认所有握手信息无误。

至此，一个安全的加密通道建立完成，后续所有数据都将被加密传输。

> **注意**：在支持HTTP/2的现代浏览器和服务端，TLS握手会通过**ALPN（应用层协议协商）** 扩展，在握手阶段就确定使用HTTP/2协议。这会对后续的数据传输效率产生影响，但握手过程本身没有变化。

#### 阶段三：HTTP请求/响应（建立SSE通道）

在安全的通道建立后，客户端会发送一个标准的HTTP GET请求，通过特定的请求头来“声明”自己要建立一个SSE连接[](https://www.processon.com/view/698bf0c44193673113155b75)：

```
http

GET /sse HTTP/1.1
Host: api.example.com
Accept: text/event-stream
Connection: keep-alive
```

服务器看到这个请求头后，会返回一个特殊的HTTP响应[](https://developer.aliyun.com/article/1617441)[](https://www.processon.com/view/698bf0c44193673113155b75)：

```
http

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```

此时，**整个握手过程结束**，SSE连接建立成功[](https://developer.aliyun.com/article/1617441)。这个HTTP连接会一直保持打开状态，之后服务器就可以通过这个连接，源源不断地向客户端推送数据了[](https://blog.csdn.net/2301_79949064/article/details/157504273)。

### 总结：一次握手，持续推送

总的来说，SSE的握手就是一次**标准的HTTPS连接建立过程**，包含了完整的**TCP三次握手**和**TLS四次握手**。

与需要频繁创建连接的**短轮询**相比，SSE最大的优势在于**只需经历这一次完整的握手过程**，之后所有数据都通过这一个长连接传输，极大地节省了反复握手带来的网络开销和延迟[](https://developer.baidu.com/article/detail.html?id=6226296)。
